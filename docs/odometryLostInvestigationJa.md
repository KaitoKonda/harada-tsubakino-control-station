11 件中 8 件が standby の OdometryLost（OTOS 7 件、wheel 1 件）です。その他は ConnectionTimeout、RosConfigMismatch、interrupted が各 1 件です。全件で elapsedSeconds は 0 行です。開始・終了時刻の差には ROS 準備や Enter 入力待ちも含まれるので、待機状態の継続時間には使えません。

提示された tp27712e1d_e54c_4042_ba0c_37b86020a501.mat の入力は wheelOdometry、トピックは /pi3/odometry/wheel、型は nav_msgs/Odometry です。現在の experimentConfig.m の既定値は otos ですが、この実行時の保存設定とは異なります。制御周期は 20 Hz、有効期限は 0.25 秒です。16:03:43 の OTOS 実行では有効期限を 0.5 秒にしても同じエラーでした。

実行順序は次のとおりです。

1. StationRunner.m:56 — waitForConnections で有効な受信を確認。
2. StationRunner.m:61 — calibrate でも測定の鮮度を確認。
3. StationRunner.m:65–67 — 操作画面と位置地図を生成し、初回描画。
4. StationRunner.m:169–170 — 待機の最初の更新で鮮度が偽なら即座に assert。
5. StationRunner.m:174 — 待機ループの pause は、その判定を通過した後。

StateEstimator.m:75–78 の判定は、最後に採用した測定の receivedAt と現在時刻の差です。RosOdometrySource.m:51–66 では、receivedAt を有効メッセージのコールバック実行時の toc で記録します。したがって OdometryLost は「ROS ノードが存在しない」という意味ではなく、「期限内に採用した測定がない」という意味です。同じ値が繰り返し届く Pose2D は正常に採用されるため、車両が静止しているだけでは期限切れになりません。

画面生成が有効期限を超え、その間に新しい有効なコールバック結果が反映されなければ、接続と校正が成功していても最初の待機更新で終了します。画面生成後の再受信待ちは現状ありません。一方、StationWindow と PositionMap には drawnow limitrate があり、コールバック処理の機会が全くない実装ではありません。実際の遅延時間は追加計測が必要です。MathWorks の drawnow 文書でも、この呼出しは描画とコールバックを処理するものとされています。

https://www.mathworks.com/help/matlab/ref/drawnow.html

wheel の nav_msgs/Odometry には、正の Header.Stamp が前回以下なら棄却する別の条件もあります（RosOdometrySource.m:57）。しかし同じ障害が Header のない OTOS の Pose2D でも起きているため、この条件だけを共通原因にはできません。

ログの制約として、RunLogger.record は controlLoop からだけ呼ばれています。接続中・校正中・画面生成中・待機中の測定履歴は保存されません。現在のログからは、最終受信から何秒経過したのか、最初の待機更新だったのか、通信が止まったのかを復元できません。

修正・検証の方針は、画面初期化と初回描画を起動準備に含め、その後にゼロ指令を維持しながら期限付きで新しい有効測定を待ち、校正と Start 許可へ進むことです。Start は準備完了まで無効にする必要があります。準備完了後の待機・運転中の途絶判定は引き続き有効にします。単に assert を削除したり、有効期限を延ばしたりする対応では原因の切分けになりません。

次回計測では、画面生成・初回描画の所要時間、待機周期番号、最終有効測定の経過秒数、受信数・採用数、Header や値の棄却理由を保存すると、UI 初期化の影響と配信側の途絶を区別できます。初回調査時点では報告のみを追加しました。以下は継続調査後の修正です。

2026-10-07 の継続対応では、利用者から実行先 PC の変更に伴って描画全般が遅くなったことも確認しました。StationRunner の起動順序を変更し、画面生成・初回描画を Vehicle 作成より前に済ませました。校正位置の初回描画後にも connectionTimeoutSeconds を上限として新しい測定を待ちます。この段階では描画前の測定がまだ有効でも準備完了とせず、Start は新測定確認後に有効になります。待機の最初の鮮度判定前にも pause を入れ、受信コールバックの実行機会を確保しています。Start が押されていても、その周期の鮮度確認を通過しなければ運転へ進みません。

待機中のタイムアウトは従来どおりです。assert の前に診断を保存し、例外文には測定の経過秒数・有効期限・測定番号を追加しました。運転中の地図描画は鮮度確認と指令処理の後へ移し、確認済みの測定と指令送信の間に地図描画を挟まないようにしました。描画処理そのものを別スレッドへ移したわけではなく、連続的な処理遅延や実際の配信途絶を無視して走行し続ける変更ではありません。

RunLogger の diagnostics に起動各段階の所要時間、待機・運転周期の時間差、車両ごとの測定年齢・測定番号・鮮度と ROS の採用／棄却カウンターを追加しました。各時刻の基準と読み方は userManualJa.md の「起動・待機中の受信エラーを調べる」に記載しています。既存の運転データ系列は変更していません。

回帰テストでは、実際の StateEstimator と 0.35 秒の描画遅延を使い、新測定を待てば開始できること、古い測定だけでは Start を許可せずタイムアウトすること、待機中の受信停止で終了すること、準備中の Stop、Start 押下時の鮮度確認、操作画面の Start 無効化を検証しました。受信停止時の診断が MAT ファイルへ保存されることと、ROS の不正値・古いヘッダーの棄却記録も確認対象にしています。実機における今回の原因の最終確認は、新しいログで initialMapDrawn と standby の測定経過時間を照合して行います。

検証結果：MATLAB R2025b Update 2 で、既存テストと新規テストの計 29 件が成功しました（全体実行後、追加した対象を再実行）。実際の画面を使う simulation の計測では、画面生成・初回描画が 6.459 秒、校正位置の初回描画が 0.948 秒で、いずれも測定の有効期限 0.25 秒を上回りました。修正後の起動順序ではこの描画を経ても simulation は正常完了しました。この値は今回のテストプロセスの実測であり、過去の実機エラー時の描画時間を復元したものではありません。遅延注入を使った experiment の回帰テストでは、新しい測定を待って正常に運転へ進むことを別途確認しています。
